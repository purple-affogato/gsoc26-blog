## Creating the MPCP Testsuite

This week, I was focused on creating the testsuite for MPCP. The tests I've planned for are:

- test_mpcp_obtain_and_release() --> simple MPCP obtain and release sequence.
- test_mpcp_flush_error() --> ensures that RTEMS_NOT_DEFINED when attempting to flush a MPCP semaphore.
- test_mpcp_deadlock_error() --> ensures RTEMS_INCORRECT_STATE is returned in a deadlock situation
- test_mpcp_nested_obtain_error() --> ensures that RTEMS_INCORRECT_STATE is returned when a task attempts to obtain a semaphore it already owns.
- test_mpcp_multiple_obtain() --> ensures the priority of a task is raised correctly when obtaining multiple MPCP semaphores of various ceiling priorities.
- test_mpcp_task_migrate_error() --> ensures that RTEMS_RESOURCE_IN_USE is returned when a task owning a MPCP semaphore attempts to migrate to another processor.
- test_mpcp_multiple_obtain_and_release() --> tests a more complicated sequence of obtaining and releasing multiple MPCP semaphores.

At the time of writing of this, I've completed writing all of these tests except test_mpcp_multiple_obtain_and_release(). The overall implementation of this testsuite, named smpmpcp01, draws a lot of inspiration from smpmrsp01 which is the testsuite for MrsP. Specifically, I took the idea of a test context structure to store the IDs for tasks, semaphores, schedulers, etc. which is pretty useful for tasks that use worker tasks. I also borrowed the SMP scheduler configuration since the simple priority SMP is simple (obviously) and deterministic enough for the tests I've planned.

In terms of things I've learned for this week, when writing test_mpcp_task_migrate_error(), I initially thought that the original MPCP implementation didn't include any mechanisms that prevented task migration since there wasn't anything that *explicity* pinned a task to a processor. As it turns out, the implementation actually uses the same functionality as the MrsP.

Both MPCP and MrsP are meant for fully-partitioned systems meaning that tasks are statically bound to processors and migration is not allowed. In RTEMS, the priority of a task is managed using priority nodes. A task at all times will have a priority node representing its real priority. When a task obtains a MPCP or MrsP semaphore, the internal functions \_MPCP_Raise_priority() and \_MRSP_Raise_priority() add a priority node to the thread obtaining the semaphore. This also means the task's current priority is higher than its real priority resulting in RTEMS_RESOURCE_IN_USE. Going further, adding a priority node also adds a wait node to the thread's scheduler. When calling a function like rtems_task_set_scheduler(), it checks if the the thread's scheduler has more than 1 wait node as one of the conditions that can lead to RTEMS_RESOURCE_IN_USE. The exact check looks like this:

```c
if (
    !_Priority_Is_empty( &old_scheduler_node->Wait.Priority )
#if defined( RTEMS_SMP )
    || !_Chain_Has_only_one_node( &the_thread->Scheduler.Wait_nodes ) ||
    the_thread->Scheduler.pin_level != 0
#endif
  ) {
```
For context, RTEMS uses chains (doubly linked lists) as the primary data structure for objects like thread queues, priority nodes, scheduler nodes, etc.

At this time, I'm not super clear on what exactly is a scheduler wait node, mostly due to the fact I'm not familiar with every feature in the RTEMS super core. The explanation on wait nodes from the source code is:

```
Scheduler nodes immediately available to the thread by its home scheduler and due to thread queue ownerships.

This chain is protected by the thread wait lock.

This chain is never empty.  The first scheduler node on the chain is the scheduler node of the home scheduler.
```

My best guess is this means that the scheduler has certain things it needs to "wait" on before doing making any changes to the thread that it's running. The way this could be managed is with wait nodes.

**TLDR: all this info means that RTEMS internal workings allow for extra priority nodes to stop tasks from migrating to other schedulers/processors.**

This is pretty convenient for me since it means I don't have to make any major changes to the MPCP implementation and I learned something new about RTEMS from this whole process. I also have better knowledge to write the documentation with later.
